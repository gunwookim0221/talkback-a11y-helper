Report 01 · Context

프로젝트 개요

접근성 검증은 화면을 한 번 보는 것으로 끝나지 않습니다. TalkBack focus 순서, 발화, 동적 content와 recovery까지 확인하고 재현 가능한 evidence로 남겨야 합니다.

왜 수동 검증이 어려운가

  • focusable object가 많고 시각적 배치와 TalkBack 순서가 다를 수 있습니다.
  • plugin 화면은 scroll, popup, overlay, lazy content와 함께 변합니다.
  • 보이는 text와 실제 speech가 다를 수 있어 두 정보를 함께 비교해야 합니다.
  • 실패 위치의 screenshot, crop, focus와 로그가 있어야 원인을 재검토할 수 있습니다.
  • 앱/plugin 변경 때 anchor, resource-id, navigation path와 recovery 규칙이 함께 흔들릴 수 있습니다.

Three layers

하나의 검증을 만드는 세 계층

Android

Android Helper

AccessibilityService 기반 APK가 ADB broadcast를 받아 tree dump, focus 이동, target action, SMART_NEXT와 evidence event를 연결합니다.

Execution

Python Runner

시나리오 진입, traversal, recovery, stop policy, 실제 focus 기반 row와 XLSX/JSON/log/evidence 저장을 조정합니다.

Control & review

QA Frontend

device/TalkBack preflight, run profile, scenario selection, Batch monitor, Review Required와 Candidate/Comparator를 제공합니다.

핵심 관점

이 시스템의 목적은 단순히 “자동으로 클릭한다”가 아닙니다. 화면에 도달한 뒤 실제 TalkBack이 방문한 focus와 발화/화면 evidence를 수집하고, 사람이 판단할 수 있는 형태로 만드는 것입니다.
